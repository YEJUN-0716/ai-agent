# 사무실 화면 — 야간 근무가 보이는 사무실 (설계)

**작성일** 2026-07-24
**상태** 설계 승인됨

## 문제

사무실 화면(`office_game/index.html` + `app.py` 의 `_rooms`)은 앱의 유일한
내비게이션이다. 그런데 이 화면이 "일하는 중" 으로 보이는 경우는 **사장이 종목을
입력했을 때 하나뿐이다.** 실제 일의 대부분은 밤에 GitHub Actions 가 한다.

2026-07-23 에 그 대가를 치렀다. 애널리스트 성적표의 기록 장치를 PR #23·#24 로
다 만들어놓고도 **기록이 하루도 쌓이지 않고 있었다.** 기록을 부르는 곳이
`signal_worker.py` 하나였는데, 그걸 돌리는 `signal-alerts.yml` 은 2026-07-20 에
크론이 주석 처리됐기 때문이다(팩터 알파 미확인으로 매수 알림 중단). 알림을
끄면서 성적표 재료도 같이 끊긴 것을 아무도 몰랐다.

그동안 사무실 화면은 평온했다. 직원들은 잡담하고 산책하고 있었다. **화면에
드러났어야 할 고장이 화면에 전혀 없었다.**

같은 종류의 눈속임이 하나 더 있다. `signal_pipeline_employee` 는
`signal_log.json` 이 5일보다 오래되면 '주의' 를 낸다. 그 잡은 의도적으로 꺼둔
상태이므로 이 경고는 **영원히 켜져 있다.** 늘 켜져 있는 경고등은 사람이 무시하게
만들고, 그래서 진짜 경고도 같이 묻힌다.

## 목표

사무실이 자동화 잡의 상태를 **상황판·직원 상태·조명** 세 겹으로 드러낸다.
잡이 도는지, 의도적으로 꺼졌는지, 밀렸는지를 구분해서 보여준다.

곁들여 화면의 완성도를 올린다 — 방별 색 아이덴티티, 벽과 창문, 책상 원근,
선택 피드백.

**비목표(이번 범위 아님)**

- 화면에서 잡을 켜고 끄거나 수동 실행하는 것. 이번 범위는 **보여주기까지**다.
  워크플로를 앱에서 조작하려면 GitHub 토큰을 앱에 쥐여줘야 하고, 그건 별개의
  보안 결정이다.
- 잡 실패 알림(텔레그램 등). 화면을 열었을 때 보이는 것까지가 이번 몫이다.
- 캐릭터 스프라이트 교체. 이모지를 유지한다.
- 사운드, 파티클 종류 추가.

## 1. 진실의 원천은 워크플로 파일이다

**잡 목록과 주기를 코드에 하드코딩하지 않는다.** 하드코딩하면 이번 고장이
그대로 재발한다 — 코드는 "매일 돈다" 고 믿는데 실제 워크플로는 꺼져 있는 상태.
그 불일치를 드러내는 게 이 작업의 목적인데, 그 목적을 스스로 무너뜨리게 된다.

`.github/workflows/*.yml` 을 `yaml.safe_load` 로 읽어 `on.schedule` 이 살아
있는지 본다. 크론이 주석 처리돼 있으면 파싱 결과에 키 자체가 없으므로 자연히
"스케줄 없음" 으로 판정된다. 나중에 누가 크론을 켜거나 끄면 사무실이 따라간다.

`pyyaml` 은 현재 설치돼 있지만 다른 패키지가 끌고 온 것이고
`requirements.txt` 에 선언돼 있지 않다. 여기에 의존하므로 명시적으로 추가한다.

## 2. 예정과 실적을 대조한다

각 잡은 결과를 저장소에 커밋해 돌려놓는다. 그 파일이 실적 기록이다.

| 잡 | 워크플로 | 실적을 읽을 곳 |
|---|---|---|
| 애널리스트 기록 | `analyst-log.yml` | `data/analyst_log/YYYY.jsonl` 의 마지막 `date` |
| IC 갱신 | `ic-update.yml` | `ic_weights.json` 의 `updated` |
| 시그널 알림 | `signal-alerts.yml` | `signal_log.json` 의 마지막 `entry_date` |
| 페이퍼트레이드 | `paper-trade-us.yml` | `equity_log.json` 의 마지막 레코드 |

`daily-report.yml`(토스 P&L)은 결과가 텔레그램으로만 가고 저장소에 아무것도
남기지 않는다. **실적을 알 방법이 없다.** 추적하는 척하지 않고 "추적 불가" 로
표시한다 — 모르는 것을 초록불로 칠하는 것이 이 프로젝트가 반복해서 고쳐 온
고장의 형태다.

**잡의 실행 성공이 아니라 결과 파일을 본다는 점이 중요하다.** 2026-07-23 에
그 차이가 드러났다. 크론을 고친 뒤에도 잡은 `data/` 가 gitignore 라 결과를
커밋하지 못했다(PR #26). 워크플로 실행 이력을 신뢰했다면 "돌았음" 으로 보였을
것이다. 저장소에 남은 것만 실적으로 센다.

예정과 실적을 대조해 상태를 낸다:

| 상황 | 상태 | 캐릭터 |
|---|---|---|
| 스케줄 살아있고 예정대로 돎 | 정상 | 평소대로 |
| 1주기 밀림 | 주의 | 빠른 맥박 |
| 2주기 이상 밀림 | 경고 | ❗ 패닉 |
| 스케줄 꺼짐(의도적) | 대기 | 💤 낮잠 |
| 결과 파일 없음 + 스케줄 살아있음 | 대기 | 💤 "첫 실행 대기" |
| 실적을 읽을 곳이 없음 | 대기 | 💤 "추적 불가" |

**꺼진 잡을 고장으로 표시하지 않는 것이 핵심이다.** 이 구분이 있어야 남은
경고가 진짜 경고가 된다.

기존 상태 어휘(정상/주의/경고/대기)와 애니메이션
(`office-pulse`/`office-pulse-fast`/`office-shake`/`office-sleep`)을 그대로
쓴다. 새 상태를 만들지 않는다.

## 3. 방과 직원

새 방 **'성과 평가팀' 📊**, 직원 **'성적표' 👩‍🏫** 하나. 나머지 자리는 기존
관용구대로 빈 책상(ghost)으로 둔다 — `quant` 성적과 전환 게이트가 나중에 앉을
자리다.

나머지 세 잡은 **이미 있는 직원에게 붙인다.** 새 사람을 만들지 않는다.

| 잡 | 담당 직원 | 방 |
|---|---|---|
| `analyst-log.yml` | 성적표 (신규) | 성과 평가팀 (신규) |
| `ic-update.yml` | 팩터 랭킹 | 시그널 생성팀 |
| `signal-alerts.yml` | 시그널 파이프라인 | 자동매매 운영팀 |
| `paper-trade-us.yml` | 계좌 현황 | 자동매매 운영팀 |

기존 세 직원의 상태 함수는 이미 각자 상태 파일을 읽는다. 바뀌는 것은 **워크플로
인식** 하나다 — 크론이 꺼져 있으면 '주의' 가 아니라 '대기'(휴직) 를 낸다.

## 4. 상황판

전광판을 40px 한 줄에서 68px 두 줄로 넓힌다. 1줄은 지금 그대로(업무 지시 /
최근 분석 / 벽시계), 2줄이 야간 근무 현황이다.

```
📊 성적표 오늘 ✅  ·  📈 IC 3일 전 ✅  ·  📡 시그널 휴직 💤  ·  💰 페이퍼 휴직 💤
```

**경고 상태 칩만 빨갛게 깜빡인다.** 평상시엔 조용하고 뭔가 죽었을 때만 시선을
끈다. 상시 점등은 무시를 학습시킨다 — 3절에서 고치는 것과 같은 실수를 새 UI 에서
반복하지 않는다.

## 5. 조명

시간대(클라이언트 시계, 벽시계에 이미 쓰는 값)로 반투명 오버레이를 깐다.
기존 `PALETTE` 는 건드리지 않고 그 위에 덮는다 — 다크모드(`dark` 인자)와 싸우지
않기 위해서다. 다크모드는 '사용자 테마', 시간대는 '극중 시각' 으로 축이 다르다.

- **주간(06–18)** 현재 모습
- **저녁(18–22)** 바닥 톤을 살짝 내리고 창밖이 노을
- **야간(22–06)** 전체를 어둡게 + **그 시간대에 도는 잡의 담당 직원 자리에만
  스탠드 조명 원뿔.** 나머지 직원은 💤

밤에 앱을 열면 실제로 그 시간에 도는 잡의 담당자만 깨어 있다. 조명이 장식이
아니라 정보가 되는 지점이다.

## 6. 그래픽

네 가지만 손댄다.

1. **방별 색 아이덴티티** — 지금 6개 방이 전부 같은 나무색이라 구분이 안 된다.
   방 헤더 바와 바닥 색조를 팀별로 나눈다.
2. **벽과 창문** — 캔버스 상단에 벽 띠와 창문. 창밖이 시간대에 따라 변한다
   (주간 하늘 / 노을 / 밤+별). 5절 조명과 **같은 데이터를 쓴다.**
3. **책상 원근** — 상판을 사다리꼴로.
4. **선택 피드백** — 지금은 원 하나뿐. 선택 시 그 방이 살짝 밝아진다.

## 7. 알려진 한계 — 로컬 저장소 신선도

로컬에서 `streamlit run app.py` 로 열면 상태 파일은 **마지막으로 git pull 한
시점** 기준이다. 잡은 잘 돌았는데 로컬이 안 당겨져 있으면 직원이 억울하게
결근 처리된다.

git 내부를 뒤지는 대신 이렇게 구분한다 — **스케줄이 살아있는 잡이 둘 이상
동시에, 비슷한 폭으로 밀렸으면** 전부 고장 났을 가능성보다 저장소를 안 당겼을
가능성이 높다. 그 경우 개별 직원을 탓하는 대신 상황판에 "저장소를 N일 안
당겼습니다" 를 띄운다.

휴리스틱이고 완벽하지 않다. 실제로 두 잡이 같은 날 깨졌다면 오진한다. 그래도
개별 직원에게 조용히 틀린 경고를 붙이는 것보다는 낫다고 판단했다 — 틀린 경고는
전체 신호를 못 믿게 만든다.

`modules/office_jobs.py` 는 `app.py` 를 import 하지 않는다(순환). 리포 루트
경로를 인자로 받아 파일을 읽는다 — 테스트가 `tmp_path` 를 넘길 수 있어야 한다.

## 9. 테스트

`modules/office_jobs.py` 는 순수 함수라 `tmp_path` 에 가짜 워크플로 yml 과 상태
파일을 만들어 전부 네트워크 없이 고정한다.

- 크론이 주석 처리된 워크플로 → 대기(휴직), **경고 아님**
- 활성 크론 + 최근 기록 → 정상
- 활성 크론 + 1주기 밀림 → 주의
- 활성 크론 + 2주기 밀림 → 경고
- 결과 파일 없음 + 활성 크론 → 대기(첫 실행 대기)
- 실적 경로가 없는 잡 → 대기(추적 불가)
- 스케줄 살아있는 잡 둘이 동시에 비슷한 폭으로 밀림 → 저장소 미당김 힌트
- 깨진 yml → 예외 없이 '알 수 없음'. **사무실 화면이 파싱 실패로 죽으면 안 된다**

`office_game/index.html` 은 기존에도 자동 테스트가 없다. 육안 확인으로 둔다 —
이번 작업에서 캔버스 테스트 하네스를 새로 세우지 않는다.

## 10. 성공 판정

**2026-07-23 의 고장이 이 화면에 떴을 것인가.** `analyst-log.yml` 의 크론을
주석 처리하고 앱을 열었을 때, 성적표 직원이 ❗ 패닉이 아니라 💤 휴직으로 바뀌고
상황판에 "성적표 휴직" 으로 표시되면 된다. 반대로 크론은 살아있는데 기록이
이틀 밀린 상태를 만들면 성적표 직원이 ❗ 로 바뀌어야 한다.

이 두 경우를 손으로 만들어 확인하는 것이 완료 조건이다.
