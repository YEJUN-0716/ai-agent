# AI 애널리스트 성적표 — 설계

**작성일** 2026-07-23
**상태** 설계 승인 대기 (섹션 1 승인됨)

## 문제

`app.py` 의 AI 애널리스트 팀은 6개 부서가 종목마다 0~100 점을 낸다. 그런데
**누가 잘 맞히는지 아무도 재지 않는다.**

방향성 3인의 가중치는 `modules/analyst_weights.py` 가 정하는데, 실측 성적이
아니라 `ic_weights.json` 의 **팩터 IC 를 대리 지표로** 쓴다:

```
차트+파동+모멘텀 ← mom_3m, mom_1m, low_vol
퀀트+재무        ← value, quality
ICT+CRT          ← ict
```

이 대리 지표에는 두 겹의 문제가 있다.

1. **팩터 IC 는 애널리스트의 성적이 아니다.** 차트 애널리스트는 기술점수 70%
   + 모멘텀 30% 로 점수를 내는데, 그 예측력을 `mom_3m`/`mom_1m`/`low_vol` 의
   IC 로 대신 재고 있다. 다른 것을 재서 이 사람의 발언권을 정하는 셈이다.
2. **하필 그 팩터들이 방금 고친 것들이다.** PR #22 에서 밝혀졌듯
   `mom_3m`/`mom_1m`/`low_vol` 은 프로덕션 스캔이 계산조차 하지 않는 정의다.
   `analyst_weights.py` 는 아직 `regime_weights`(페이퍼트레이드용 블록)를 읽고 있다.

그리고 재료가 아예 없다. 애널리스트팀은 Streamlit 화면에서 사람이 종목을 칠 때만
돌고, 판단이 어디에도 저장되지 않는다. `signal_log.json` 에는 합산 점수만 남는다.
자동 스캔(`signal_worker.py`)은 애널리스트팀을 호출하지 않는다.

## 목표

애널리스트별 판단을 자동으로 남기고, 실제 수익률과 대조해 **실측 성적표**를 만든다.

**비목표(이번 범위 아님):** 성적에 따라 가중치를 자동으로 바꾸는 것. 표본이
쌓이기 전에는 판정할 수 없고, 근거 없이 비중을 바꾸는 것이 바로 지금 고치는
고장의 형태다. 전환 조건은 아래 3절에 명시하되 구현은 다음 작업으로 미룬다.

## 1. 기록과 채점 (승인됨)

### 왜 세 기간으로 채점하는가

21일 간격으로 채점하면 판정 표본이 **연 12개**씩 쌓인다. n=30 에 2.5년이 걸린다.
이걸 모르고 시작하면 1년 뒤에도 아무 결론을 못 낸다.

그래서 **5일 / 21일 / 63일** 선행수익률로 동시에 채점한다. 5일 기준은 표본이
연 50개씩 쌓여 약 7개월이면 판정 가능하다. 21일은 기존 팩터 IC 와 같은 기준이라
나란히 비교된다. 63일은 느린 신호용이다. 재료(점수 기록)는 하나이고 채점만 세 번
하므로 추가 수집 비용이 없다.

### 겹치는 창 보정

매일 기록하면 관측치의 선행 구간이 서로 겹쳐 실제보다 표본이 많아 보인다.
보정하지 않으면 "n=250, 유의함" 이라고 착각하게 된다 — PR #22 에서 다룬 것과
같은 종류의 함정이다.

표준오차는 겹침을 반영해 계산한다(Newey–West, lag = 선행일수 − 1). 겉보기 n 과
**유효 표본 수를 함께 표시**해 둘을 혼동하지 않게 한다.

### 저장

```
data/analyst_log/YYYY.jsonl     # 한 줄에 하루치
{"date":"2026-07-23","regime":"bull","scores":{"AAPL":{"chart":62.1,"quant":55.0,"ict":48.5}, ...}}
```

- 연도별 파일 분리. 점수는 소수 1자리로 절삭.
- 276종목 × 3인 ≈ 828개 숫자/일 → 연 약 3MB. 커밋 가능한 크기다.
- 기존 `signal_log.json` 과 같이 워크플로가 커밋해 되돌린다.
- 애널리스트 키는 표시 이름(한글) 대신 안정적인 슬러그(`chart`/`quant`/`ict`)를
  쓴다. 표시 이름이 바뀌어도 과거 기록과의 연결이 끊기지 않는다.

## 2. 애널리스트를 자동 경로에서 돌리기

### 대상은 방향성 3인만

`chart`(차트+파동+모멘텀), `quant`(퀀트+재무), `ict`(ICT+CRT) 만 기록한다.
나머지 3인은 종목별 방향성 점수가 아니라서 성적표 대상이 아니다 — 매크로+금리는
종목과 무관한 단일 값이고, 백테스팅팀은 신뢰도 플래그, 리스크팀은 Kelly 사이징
역할이다(`build_analyst_report` 의 `role` 구분과 같다).

### 추출

`app.py:3679-3730` 의 세 함수를 `modules/analyst_team.py` 로 옮긴다.
`factor_scoring.py` 를 app.py 에서 떼어낸 것과 같은 패턴이다. app.py 는 새 모듈을
호출만 하고, 점수 산식은 모듈이 소유한다.

Streamlit·yfinance 를 import 하지 않는다. 입력(기술점수·재무점수·OHLCV)은 호출부가
넘긴다. 그래야 자동 경로와 화면이 같은 산식을 쓴다.

**동작 무변경을 테스트로 고정한다** — 추출 전후 같은 입력에 같은 점수가 나와야 한다.

### 배선

`signal_worker.py` 가 매일 스캔 후 세 애널리스트를 호출해 `analyst_log` 에 기록한다.
이미 276종목의 가격·재무를 받아 오므로 데이터 수집이 추가되지 않는다.

### 알려진 한계 — 재무 애널리스트는 과거 재현 불가

`quant` 는 yfinance `.info`(현재 스냅샷) 기반이라 과거 시점 재현이 안 된다.
**앞으로 남기는 기록은 문제없다** — 기록 시점의 스냅샷이므로 look-ahead 가 아니다.
과거를 소급해 채울 수 없을 뿐이다. `chart`/`ict` 는 OHLCV 만 쓰므로 깨끗하다.

## 3. 성적을 언제 가중치에 반영하나 (승인 필요)

### 전환 게이트

성적표가 가중치를 바꾸는 조건은 **둘 다** 충족일 때다.

- 유효 표본 n ≥ 30 (겉보기 n 아님)
- 애널리스트 간 IC 차이가 짝지은 기준으로 |t| ≥ 2.0

`PAIRED_T_THRESHOLD` 와 같은 기준을 쓴다. 조건 전에는 현행 가중치를 유지한다.

### 그 전까지

성적표는 **표시만** 한다. 화면에 애널리스트별 IC·적중률·유효 표본 수를 띄우고,
가중치에는 손대지 않는다. 보스가 눈으로 축적을 확인할 수 있게 하는 것이 목적이다.

### 곁다리 수정

`analyst_weights.py` 가 `regime_weights`(페이퍼트레이드 블록)를 읽는 문제는 이번에
같이 고친다. 전환 전까지의 폴백도 프로덕션이 실제로 쓰는 쪽을 보아야 한다.
PR #22 가 만든 `production_weights` 를 우선 읽고, 없으면 기존 경로로 후퇴한다.

## 구성 요소

| 모듈 | 책임 | 의존 |
|---|---|---|
| `modules/analyst_team.py` | 방향성 3인의 점수 산식 (순수) | 없음 (Streamlit·yfinance 미사용) |
| `modules/analyst_log.py` | 기록 append / 조회 | 파일 IO |
| `modules/analyst_scorecard.py` | 채점 — IC·적중률·겹침 보정 표준오차 | numpy, scipy |
| `signal_worker.py` | 매일 기록 호출 | 위 셋 |
| `app.py` | 성적표 표시 | `analyst_scorecard` |

각 모듈은 독립적으로 테스트 가능하다. 채점기는 파일이나 네트워크를 모르고 숫자만
받는다 — 겹침 보정 산술을 합성 데이터로 검증할 수 있어야 한다.

## 에러 처리

- 기록 실패가 일일 스캔을 죽이면 안 된다. 예외를 잡아 경고만 남기고 스캔은 계속한다.
- 특정 종목의 애널리스트 점수 계산 실패는 그 종목 키를 **빼서** 기록한다.
  중립값(50)으로 채우면 '계산 불가'가 '중립 판단'으로 성적에 섞인다.
  (PR #22 에서 12-1 모멘텀에 적용한 것과 같은 규칙.)
- 채점 시 유효 종목 5개 미만인 날은 그 날을 건너뛴다.

## 테스트

- `analyst_team` 추출 전후 점수 동일성 (동작 무변경 고정)
- 기록 포맷 왕복(write→read) 및 결측 키 처리
- 겹침 보정 표준오차 — 독립 표본에서는 통상 SE 와 일치하고, 완전 겹침에서는
  유효 표본이 줄어드는지 합성 데이터로 검증
- 게이트 — n 부족 / |t| 미달일 때 가중치가 바뀌지 않는지
- `analyst_weights` 폴백이 `production_weights` 를 우선 읽는지

## 재현·운영

- 기록: 매일 `signal_worker.py` (기존 워크플로에 편승)
- 채점: 화면 진입 시 계산 (기록 파일만 읽으므로 빠름)
- 첫 판정 가능 시점: 5일 기준 약 7개월 후 (연 50 표본 기준 n≈30)
