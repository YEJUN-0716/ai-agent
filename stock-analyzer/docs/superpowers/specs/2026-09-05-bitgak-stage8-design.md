## 0. 왜 이 단계가 있고, 왜 이만큼만 하는가

7단계는 **걸 수 있는 주문 위에서** ①②③ 을 전부 통과했다(n=94,310, ① +0.029R
하한 +0.024, ② +0.032R, ③b 하한 +0.0129R). 그런데 비용 여유가 **7.7bp** 라
사전 등록 §7.2 의 「3~10bp = 보류」 구간에 떨어졌다. 통과선은 10bp 였다.

### 0.1 노선을 가르는 건 7.7bp 하나다

한동안 **거짓 진입 11.1%** 가 7.7bp 보다 큰 위협일 수 있다고 봤다. **아니다 —
그건 7단계가 이미 쟀다.** 종가 문턱을 δ중위만큼 내려 같은 코드로 다시 스캔한 행:

| | n | ① | ① 하한 | ② 차이 |
|---|---|---|---|---|
| 판정 행 | 94,310 | +0.029R | +0.024 | +0.032R |
| **문턱을 δ만큼 내린 행** | **96,621 (+2.5%)** | **+0.031R** | **+0.025** | **+0.032R** |

**15:50 결정이 끌어들이는 추가 트레이드는 성적을 안 흔든다.** 그러므로 이 노선을
가르는 질문은 **7.7bp 안에 실제 비용이 들어오는가** 하나뿐이고, **그 답은
페이퍼에 없다**(§4). 실계좌에만 있다.

### 0.2 그래서 배관 질문을 둘로 쪼갠다

| | 무엇 | 어디서 답하나 |
|---|---|---|
| **되긴 되는가 (성립)** | MOC body 가 맞는가 · 지정가 매도가 있는가 · 다리가 매일 정정되는가 · 한쪽 체결되면 반대쪽이 취소되는가 · 러너 선값이 하네스와 같은가 | **이 문서 (8단계)** |
| **매일 안정적으로 되는가 (신뢰도)** | 접수·체결 비율 · 지각 0일 · 무개입 완주 비율 | **9단계 실계좌 첫 관문** |

신뢰도를 페이퍼에서 4주 재고 실계좌에서 또 재면 **같은 걸 두 번 하는 것**이다.
7단계 측정 문서 §10 이 이미 그 자리를 지정해 뒀다.

> **15:50 이 안 되면 갈아탈 자리가 없다**(참고 F 사망). 그러니 실계좌 사전
> 등록의 첫 관문은 성과가 아니라 **MOC 체결 자체**여야 한다.

**성립은 안 건너뛴다.** 유령 주문과 초과 매도는 실계좌에서 **돈이 새는 종류**라,
그게 안 난다는 걸 페이퍼에서 먼저 봐야 한다. 그리고 배관 코드는 9단계에서
어차피 필요하다 — 여기서 만드는 게 낭비가 아니다.

이 저장소는 배관을 안 밟고 넘어간 자리에서 이미 데었다. 자동 인덱스 운용은
드라이런을 다 통과하고 실전 리허설에서 보고서 결함이 나왔다 — **드라이런은
실전 경로의 절반을 안 밟는다**(`index-autopilot-plan`).

### 0.3 이번 단계의 질문 하나

> **7단계가 잰 규칙이 요구하는 주문 네 종류가, 하네스와 같은 선 위에서, 제시간에,
> 규칙이 센 것과 정확히 1:1 로, 틀린 사건 없이 실제로 나가는가.**

성과가 아니다. 기대값도 아니다. 비율도 아니다. **성립하는가**다.

## 1. 판정선 — 다섯 개, 전부 배관, 전부 「성립」

관측 전에 못 박는다. **다섯 개 중 하나라도 못 넘으면 배관 실패**이고, §8 갈래대로
고치고 다시 잰다. **비율 문턱이 아니라 「최소 1건 성립 + 틀린 사건 0」이다.**

| | 무엇을 묻는가 | 문턱 | 어디 |
|---|---|---|---|
| **도구 게이트** | 러너가 보는 채널선이 하네스와 같은 선인가 | 종목-일 **전부 1e-6 이내 일치** | §2.5 |
| **① 주문** | 네 종류가 실제로 나가고 채워지는가 | 종류마다 **≥1건 성립**, **분류 안 된 거절 0건** | §3.1 |
| **② 마감** | 15:50 ET 안에 나가고, 중복이 안 나는가 | **지각 0일 / 5 거래일**, **중복 주문 0건** | §3.2 |
| **③ 대조** | 규칙이 센 것과 실제 주문이 1:1 인가 | **불일치 0건** | §3.3 |
| **④ 유지** | 다리가 매일 그날 선값으로 살아 있는가 | 포지션-일 **100%**, **초과 매도 0건** | §3.4 |
| **⑤ 운영** | 사람 손 없이 하루가 끝나는가 | 무개입 완주 **≥4/5**, **코드 결함 개입 0건** | §3.5 |

**표본 문턱**: 진입 MOC 제출이 **15건 미만이면 「미측정」**. 건수가 모자란다고
문턱을 낮추지 않는다.

**여기 없는 것에 주목할 것.** 접수율 98% 같은 **비율 문턱을 안 둔다.** 5 거래일
표본으로 98% 를 말하면 그건 신뢰구간이 아니라 희망이다. 비율은 9단계 몫이다.

## 2. 무엇을 안 바꾸는가

### 2.1 규칙 — 전부 봉인

**A~H 는 손대지 않는다.** A(스윙 L=5) · B(매물대=볼륨프로파일) · C(손절=한 칸
아래 선) · D(252봉·50빈) · E(가장 최근 확정 변곡점) · F(익절 12선 밖 허용) ·
G(타임아웃 포함) · H(비용 = 트레이드마다 고정 R). 채널선 12개, 최저선 진입
금지, 종목당 동시 1포지션, 보유 40봉, `MIN_RISK_PCT` 0.1%, 추세변곡 35%.

**자유도 I·J 도 손대지 않는다.** I-a(돌파 후 안착) + I-b(지지 확인) 둘 다,
J-1 종가 MOC 진입 · J-2 스톱 · J-3 지정가 · J-4 40봉째 MOC.

**유동성 컷도 그대로**: 진입일 직전 20거래일 중위 거래대금 **500만 달러 이상**
그리고 종가 **5달러 이상**. 7단계 참고 E 가 2,000만에서 더 좋게 나왔지만
(여유 8.2bp) **문턱은 500만 하나뿐이고 안 바꾼다.**

**진입 형태를 안 고른다.** 7단계 참고 D 에서 I-b 단독이 판정 행보다 모든 칸에서
좋았다(+0.034R / 여유 9.6bp). **그래도 I-a+I-b 로 간다.** 그쪽으로 가려면 I-b
하나만 적은 새 사전 등록이지, 이 문서가 아니다(7단계 §3.1).

**그리드 서치 금지.** 이 문서는 새 자유도를 열지 않는다. 아래 §2.2~2.4 는
자유도가 아니라 **번인 운영 파라미터**다 — 성과 판정에 안 들어가므로 여기서
값까지 확정하고, 결과를 보고 바꾸지 않는다.

### 2.2 번인 운영 파라미터 (봉인)

| | 값 | 왜 |
|---|---|---|
| 계좌 | **Alpaca 페이퍼** (`_PAPER_BASE`) | |
| 방향 | **롱만** | 판정 행이 원래 롱만이다. 저저고·고고저 채널 둘 다 그리지만 트레이드는 전부 롱 |
| 명목 목표 | **트레이드당 약 1,000달러** | 배관은 크기를 안 탄다. 작게 잡아 자본 제약이 ③ 대조를 덜 오염시키게 |
| 수량 | `max(1, floor(1000 / 진입일 15:50 가))` — **정수** | |
| 하루 신규 진입 | **최대 5건** | |
| 동시 보유 상한 | **안 둔다** | 5일 × 5건 = 최대 25 포지션 · 명목 약 2.5만 달러. 페이퍼 10만 달러 안이라 상한이 발동할 수 없다 — 발동 못 하는 파라미터는 안 만든다 |
| 선정 규칙 | 그날 발동 중 `zlib.crc32(f"{YYYY-MM-DD}:{symbol}")` **오름차순 하위 5** | 결정적·재현 가능하고 **여유·성과와 무관**. 위약 팔과 같은 씨앗 관행 |
| 드라이런 | **2 거래일** (주문 안 냄) | |
| 번인 창 | **5 거래일** | §2.4 |
| 종료 | 번인 **5 거래일째 장 마감**, 남은 포지션 전부 **타임아웃 MOC 청산** | §2.4 |

**선정 규칙을 여유(선을 넘긴 폭)나 성과로 안 정한다.** 여유가 큰 것만 고르면
②·③ 이 쉬워지는 쪽으로 표본이 쏠린다 — 배관을 재는 자가 배관에 유리한 날만
보게 된다.

**정수 수량이 만드는 편향은 이 단계에서 무해하다.** `fill-fidelity-prereg` 가
잡은 그 편향은 성과를 잴 때 문제이고, 여기서는 성과를 안 잰다.

### 2.3 계좌 위생 — 남의 포지션 10종목 (먼저 정한다)

페이퍼 계좌에 이전 실험이 남긴 포지션 10종목이 있다(`alpaca-migration-plan`).
**둘 다 한다.**

1. **비운다.** 번인 시작 전 기존 포지션 전량 시장가 청산 + 미체결 주문 전량
   취소. 태그로만 가르지 않는 이유: 남은 포지션이 **매수여력을 먹고**, 그중
   하나라도 빗각 유니버스와 겹치면 「종목당 동시 1포지션」 규칙과 충돌해
   ③ 대조가 노이즈가 아니라 **오염**이 된다.
2. **그래도 태그를 붙인다.** 이 번인의 모든 주문에 `client_order_id` 접두사
   **`bitgak8-`** (`bitgak8-{YYYYMMDD}-{symbol}-{leg}`). 나중에 누가 이 계좌를
   또 쓰더라도 대조가 깨지지 않는다. 그리고 이 접두사가 **§3.2 멱등성의
   열쇠**다 — `_find_by_client_order_id` 가 이미 있다.

**청산이 안 끝났으면 번인을 시작하지 않는다**(§8 갈래).

### 2.4 왜 5 거래일인가

40봉 보유는 **8주**다. 20 거래일도 4주다. 둘 다 **신뢰도**를 재는 창이고,
신뢰도는 §0.2 대로 9단계 몫이다. **성립은 며칠이면 드러난다** — MOC body 가
틀렸으면 첫날 첫 주문에서 거절이고, 다리 상호 취소가 없으면 첫 체결에서 초과
매도다.

**5 거래일째 장 마감에 남은 포지션을 전부 타임아웃 MOC 로 청산한다.** 성과
관측이 아니라 **J-4 경로를 실제로 밟는 것**이다 — 판정 행의 6,769건(7.2%)이
지나가는 다리인데, 안 밟고 넘어가면 그게 정확히 「드라이런은 실전 경로의 절반을
안 밟는다」의 자리가 된다.

**따라서 이 단계는 40봉 유지도, 자연 만기도 못 본다.** §9 에 적고 9단계로 넘긴다.

### 2.5 도구 게이트 — 자를 먼저 검사한다

> **러너가 계산한 그날의 채널선(진입선·손절선·익절선)이, 같은 종목-일에 대해
> 하네스(`pilot_bitgak_power.scan()`)가 쓰는 값과 절대오차 1e-6 이내로 일치해야
> 한다. 최근 60 거래일 × 판정 행 유니버스 전부에서 오프라인으로 돌린다.
> 한 건이라도 어긋나면 이 단계를 진행하지 않는다.**

**이게 이 문서에서 가장 중요한 검사이고, 달력을 하나도 안 쓴다.** 채널선은
**기울어져 있어서 매 봉 값이 바뀐다**(명세의 함정 항목). 러너가 하네스와 다른
선을 보면, 배관이 아무리 매끄럽게 돌아도 그건 **7단계가 잰 규칙이 아닌 다른
규칙**을 실행하는 것이다. 그러면 번인도 9단계도 아무것도 검증하지 않는다.

7단계에서 하네스 자체는 6단계 재현이 정확히 나왔다. 새로 생기는 건 **러너 쪽
경로**뿐이고, 그래서 러너를 하네스에 맞춰 검사한다 — 반대가 아니다.

## 3. 판정선 다섯, 하나씩

### 3.1 ① 주문 — 네 종류가 실제로 나가고 채워지는가

> **판정: 아래 넷이 **각각 최소 1건** 접수되고 의도대로 처리됐고,
> **분류 안 된 거절이 0건**이다.**

| 종류 | 성립의 정의 | 어디서 |
|---|---|---|
| **진입 MOC** (J-1) | 접수 → **당일 종가로** 체결 | 번인 |
| **타임아웃 MOC** (J-4) | 접수 → **당일 종가로** 체결 | 번인 5일째 |
| **스톱 매도** (J-2) | 트리거 → 체결 | **프로브** (아래) |
| **지정가 매도** (J-3) | 지정가 도달 → 체결 | **프로브** (아래) |

**스톱·지정가 체결은 프로브로 밟는다.** 5 거래일 안에 손절선·익절선에 실제로
닿는다는 보장이 없다. 그래서 번인과 **분리해서**, 임의 종목 1주로 스톱을 현재가
바로 아래 · 지정가를 현재가 바로 위에 걸어 **몇 분 안에 터지게** 한다.
`scripts/measure_paper_slippage.py` 가 이미 하는 짓이라 코드가 있다.

> **프로브는 체결 **경로**가 도는지만 본다. 체결 **가격**은 안 본다**(§4).
> 프로브 트레이드는 장부에도 ③ 대조에도 들어가지 않는다 — 접두사를
> `bitgak8probe-` 로 갈라 둔다.

번인 중에 스톱·지정가가 자연히 체결되면 **그것도 성립으로 센다**(프로브보다
좋은 증거다). 안 나면 프로브로 충분하다.

**거절·미체결은 사유별로 전부 분류해서 적는다** — MOC 미지원 종목인지, 시각을
넘겼는지(②로 넘어간다), 매수여력이 없었는지(§3.3 의 사전 등록된 예외), 수량이
0 이었는지, 아니면 우리 코드가 만든 오류인지. **분류 안 된 거절이 한 건이라도
남으면 ① 은 통과가 아니다.**

**MOC 체결가와 공식 종가의 차이도 기록한다 — 판정 아님.** 페이퍼라 하한이고
(§4), 여기 넣으면 그게 §4 가 금지한 짓이다. 9단계에 넘기는 관측치다.

### 3.2 ② 마감 — 15:50 ET 안에 나가고, 중복이 안 나는가

Alpaca MOC 제출 컷오프는 **15:50 ET** 다. 그 시각에 우리는 종가를 아직 모른다 —
7단계가 δ(막판 이동 중위 14.9bp)와 거짓 진입 11.1% 로 잰 그 구조이고, §0.1 이
그 성적 영향을 이미 봤다.

> **판정: 5 거래일 전부 15:50 ET 전에 제출됐고, 중복 주문이 0건이다.**

**중복이 여기 있는 이유 — 대책이 위험을 하나 만들기 때문이다.** 이 저장소의
크론 워크플로는 **전부 장 마감 뒤에 돈다**(21:30·22:07·22:37·22:52 UTC). 장중
마감 시각을 지켜야 하는 워크플로는 **하나도 없었다.** 새로 생기는 위험 둘:

- **GitHub Actions 예약 실행은 지연된다.** 부하가 몰리면 수 분에서 수십 분
  밀리고, 드물게 건너뛴다. 마감 뒤 워크플로에서는 무해했던 성질이 여기서는
  판정선을 직접 때린다.
- **서머타임.** cron 은 UTC 고 ET 는 매년 두 번 한 시간 움직인다. 마감 뒤
  워크플로는 안전 구간이 넓어 DST 가 안 보였다. 15:50 짜리 창에서는 **한 시간
  통째로 빗나간다.**

**대책: 크론을 15:30~15:45 사이에 넷 흩뿌리고, 제출을 멱등하게 만든다.**
한 번 밀려도 다른 하나가 들어온다. 자택 러너를 되살리기 전에 이걸 먼저 쓴다 —
YAML 몇 줄이고, 멱등성에 필요한 `client_order_id` 조회는 이미 코드에 있다.

**그 대신 같은 종목에 주문을 두 번 낼 위험이 생긴다.** 그래서 「중복 0건」이
판정선이다. 대책이 만든 위험을 판정선에 안 넣으면, 대책을 안 잰 것이다.

같이 적는다(판정 아님): 크론 넷의 실제 기동 시각, 몇 번째가 이겼는지, 러너
기상부터 제출까지 걸린 시간.

**5일 무지각은 「안 밀린다」의 증명이 아니다.** ② 는 **밀렸다는 반증**만 세게
준다. 비율은 9단계 몫이다.

### 3.3 ③ 대조 — 규칙이 센 것과 실제 주문이 1:1 인가

**무엇에 대조하는가가 핵심이다.** 러너가 15:50 에 결정하는 집합과, 종가가
확정된 뒤 하네스가 세는 집합은 **다르다**(7단계: 거짓 진입 11.1%). 그러므로,

> **판정 대조는 「러너의 15:50 스캔 결과 × 선정 규칙」 대 「실제 제출 주문」이다.**
> 양방향으로 **불일치 0건**:
> - **유령 주문** — 제출됐는데 그날 15:50 스캔·선정에 없던 것
> - **누락** — 15:50 스캔·선정에 있었는데 제출 안 된 것

사전 등록된 예외 하나(누락으로 안 센다, 대신 **건수를 반드시 보고한다**):
매수여력 부족으로 막힌 것. 자본·자리 제약은 7단계가 판정에서 제외한 축이고
(`pending-order-cash-block`), 여기서 되살리지 않는다. **그 외의 모든 누락은
불일치다.**

**같이 재는 것 — 판정 아님:**

> 종가 확정 뒤 하네스를 같은 날에 돌려, **15:50 스캔 집합 ↔ 종가 확정 집합**의
> 차이를 실측한다. 7단계는 이 값을 δ 중위와 여유 분포로 **추정**해서 11.1% 를
> 냈고, 그 δ 는 IEX 프린트라 **하한**이었다(마감 경매 프린트가 없어 실제로는
> 15:50→15:59 를 쟀다). 여기서는 **실제 종가**로 잰다.

5 거래일 표본이라 11.1% 를 갱신할 자가 못 된다. **부호와 자릿수만 본다.**
크게 어긋나면 9단계 사전 등록이 그걸 먼저 다룬다.

### 3.4 ④ 유지 — 다리가 매일 그날 선값으로 살아 있는가

체결이 확정되면 포지션마다 다리가 둘 붙는다: 손절 **스톱 매도**(J-2), 익절
**지정가 매도**(J-3). 그리고 **채널선이 기울어져 있어서 두 값은 매 거래일
바뀐다.**

> **판정 (포지션-일 기준, 청산 당일 제외):**
> - 보유 중인 포지션마다 스톱 1건 + 지정가 1건이 **살아 있고**, 그 가격이
>   **그날의 하네스 선값과 반올림 오차 이내로 일치** — **100%**
> - **초과 매도 0건** — 음수 포지션, 중복 청산, 보유 수량보다 많은 매도 주문

**두 갈래가 동시에 살아 있다는 게 이 다리의 어려운 점이다.** 한쪽이 체결되면
다른 쪽을 **반드시** 취소해야 한다. 안 하면 없는 주식을 판다 — 페이퍼에서는
장부가 틀리고, 실계좌에서는 **돈이 새는 종류**다. **성립 검사를 실계좌 앞에
두는 이유가 정확히 이 줄이다.**

**5일이 보는 것과 못 보는 것:** 정정 **동작**은 첫날부터 매일 돌므로 5일이면
성립이 드러난다. 40봉 누적 표류와 기업행위는 **못 본다** — §9.

같이 보고(판정 아님): 정정 건수·실패·재시도·rate limit. 9단계 사이징 설계의
입력이다.

### 3.5 ⑤ 운영 — 사람 손 없이 하루가 끝나는가

> **판정: 5 거래일 중 사람이 한 번도 개입하지 않고 스캔→제출→체결확정→
> 다리 등록/정정까지 끝난 날이 4일 이상이고, 그중 **코드 결함으로 인한 개입이
> 0건**이다.**

외부 원인(브로커 장애·시세 지연) 개입은 **1건까지 허용하되 분류·보고**한다.
코드 결함이면 **0건**이 문턱이다 — 고치고 5 거래일을 다시 센다.

개입은 **전부 기록하고 분류**한다: 러너가 안 깼다 / 시세를 못 받았다 / 주문이
막혔다 / 우리 코드가 죽었다 / 사장님이 멈췄다. **분류가 곧 9단계 숙제 목록이다.**

하루 운영 흐름(이게 실제로 도는지가 ⑤ 다):

| 시각 (ET) | 무엇 |
|---|---|
| 15:30 / 15:35 / 15:40 / 15:45 | 크론 넷. 각자 ET 시계 검사 — 창 밖이면 즉시 종료 |
| (이긴 회차) | 유니버스 · ADV 20일 중위 · 5달러 컷 · 사다리 스캔 · I-a/I-b 발동 · 선정 5건 · **보유 봉수 계산** |
| (이긴 회차) | **접두사로 오늘 주문 조회 → 이미 냈으면 아무것도 안 한다**(멱등) |
| (이긴 회차) | **진입 MOC 제출** + **40봉째 포지션 타임아웃 MOC 제출** |
| **15:50** | **브로커 컷오프.** 이후 제출은 거절 |
| 16:15 이후 | 체결·수량 확정 조회 → 장부 기록 |
| 16:15 이후 | 신규 포지션에 스톱·지정가 등록, 기존 포지션 두 다리 **전부 정정**, 한쪽 체결분은 **반대 다리 취소** |

타임아웃이 제출 줄에 같이 있는 이유: 청산이 **40봉째 종가**라 그날 MOC 를 내야
한다. 그래서 **보유 봉수 계산이 진입 스캔과 같은 창에 들어간다.**

## 4. 판정선에 **안** 넣는 것 — 슬리피지와 기대값

**이 문서는 슬리피지도 기대값도 판정하지 않는다.** 재지 말라는 게 아니라
**판정선에 못 올린다**는 뜻이다. 관측치는 기록하고 9단계로 넘긴다.

이유는 자가 없어서다.

- **Alpaca 페이퍼는 대기열도 시장충격도 없이 달라는 값에 채워준다.** 3a.5 에서
  실측한 왕복 손절 슬리피지가 **0.98bp** 였다(`paper-slippage-measured`). 그건
  실력이 아니라 **시뮬레이터의 성질**이고, 그 문서가 스스로 "**하한**"이라고
  적었다.
- **7단계 사전 등록 §5.2 가 페이퍼 체결을 기준선에서 명시적으로 뺐다.** 같은
  이유로 뺀 것을 8단계에서 슬쩍 되살리면, 7단계가 봉인한 기준선을 우회하는
  것이다.
- **마감 경매는 페이퍼가 참여하지 않는다.** MOC 의 진짜 질문은 "공식 종가에서
  얼마나 벌어지는가"인데, 시뮬레이터는 종가를 **알고 나서** 채워준다. 7단계
  측정 문서 §10 이 "모르는 건 마감 경매(MOC) 체결이 공식 종가에서 얼마나
  벌어지는가"라고 적은 그 항목은 **여기서도 모른 채로 남는다.**

**7.7bp 는 페이퍼로 답할 수 없다.** 답한 척하면 가정을 숫자로 위장하는 것이고,
이 저장소는 정확히 그 짓으로 한 번 데었다 — 장부 체결가는 관측이 아니라
백테스트와 같은 식의 계산값이라 짝지어 빼면 0 이 나왔다(`fill-fidelity-prereg`).
페이퍼 슬리피지를 여유 계산에 넣는 건 같은 병의 다른 얼굴이다.

**그리고 기대값도 안 잰다.** 5 거래일 · 최대 25 트레이드 · 대부분 강제 청산인
표본으로 낸 평균 R 은 7단계의 94,310건과 나란히 놓을 물건이 아니다. **번인의
성적이 좋든 나쁘든 노선 판정은 안 바뀐다.** 이 문장을 미리 못 박는다 — 숫자를
보고 나서 "그래도 참고는 되지 않나"로 미끄러지는 게 사전 등록이 깨지는 방식이다.

## 5. 번인이 통과해도 노선은 「보류」다

**이 문서는 실전 투입을 승인하지 않는다.**

7단계 §7.2 는 여유 3~10bp 를 **「보류. 실계좌 소액 실측 없이는 못 넘는다」**로
못 박았다. 8단계는 그 문장을 건드리지 않는다 — 배관 질문은 여유 질문과 **다른
질문**이고, 다른 질문에 답한다고 앞 질문이 풀리지 않는다.

| | 답하는 문서 |
|---|---|
| 규칙이 무작위보다 나은가 | 7단계 — **답했다**(①②③ 통과) |
| **주문이 성립하는가** | **8단계 — 이 문서** |
| 매일 안정적으로 되는가 | **9단계 첫 관문** |
| 7.7bp 안에 실제 비용이 들어오는가 | **9단계 — 실계좌 소액, 별도 사전 등록** |

8단계 전부 통과 = 「9단계로 갈 자격이 생겼다」이지 「실전 투입」이 아니다.
8단계가 깨지면 9단계를 시작하지 않는다.

## 7. 미리 아는 결함 — 지금 적어 둔다

### 7.1 `modules/alpaca_trading.py` 에 MOC 주문이 없다

현재 있는 주문은 넷뿐이다: `place_notional_buy`(시장가·day), `place_limit_buy`
(지정가·기본 gtc), `place_market_sell`(시장가·day), `place_stop_sell`(스톱·day).
**MOC 가 없다.** `type: "market"` + `time_in_force: "cls"` 를 **새로 짜야 한다.**

**이건 백테스트로는 절대 안 걸리는 종류의 결함이다.** 7단계 하네스는 "40봉째
종가"를 배열에서 읽으면 그만이고, 그 값을 실제로 받아내는 주문이 코드에 있는지
없는지 모른다. `index-autopilot-plan` 이 남긴 **「드라이런은 실전 경로의 절반을
안 밟는다」가 정확히 이 자리다.**

**결함은 하나가 아니라 넷이다** — 전부 새로 짠다:

| 없는 것 | 왜 필요한가 |
|---|---|
| **MOC** | J-1 진입 · J-4 타임아웃. 규칙의 진입 다리 자체가 없다 |
| **지정가 매도** | `place_limit_buy` 는 **매수만**이다. J-3 익절 다리가 아예 없다 |
| **주문 정정(PATCH)** | 기울어진 선을 매일 따라가려면 정정이 필요하다(§3.4) |
| **스톱의 GTC** | `place_stop_sell` 은 `time_in_force: "day"` **하드코딩**이다. 40봉 보유 중 매일 다시 걸어야 한다 |

`place_limit_buy` 의 docstring 이 이미 경고한 자리이기도 하다 — "이건 **진입만**
건다. 손절·목표 라인은 아직 안 붙는다. (…) 그건 백테스트가 잰 적 없는 체결
규칙이라 따로 정하고 재야 한다." **8단계가 그 「따로」다.**

**이 넷은 9단계에서 어차피 필요하다.** 여기서 만드는 게 낭비가 아니라는 게
번인을 5일로 줄여도 되는 이유이기도 하다 — 줄이는 건 **달력**이지 **코드**가
아니다.

### 7.2 페이퍼 계좌에 남의 포지션 10종목이 있다

§2.3 에서 정했다: **비우고, 그래도 태그를 붙인다.**

| 진입 MOC 제출 < 15건 | **「미측정」.** 창을 늘려 다시 잰다 |
| ① 네 종류 중 하나라도 성립 안 함 | **배관 실패.** 고치고 다시 5 거래일. 사유가 "MOC 자체가 이 계좌·이 종목에서 안 된다"면 **노선의 구조 문제** — 진입 규약(J-1)이 못 서므로 7단계 판정 행이 실행 불가능해진다. 그건 새 사전 등록 사안이다 |
| ① 분류 안 된 거절 ≥ 1건 | **배관 실패.** 사유를 끝까지 밝히고 다시 5 거래일 |
| ② 지각 ≥ 1일 | **배관 실패.** 크론 넷으로도 못 지켰다는 뜻이다. **자택 러너를 되살리고** 다시 5 거래일 — 「클라우드 크론으로는 15:50 을 못 지킨다」가 결론이 된다 |
| ② 중복 주문 ≥ 1건 | **배관 실패.** 멱등성이 안 선 것이다. 대책이 만든 위험이라 우선순위 높다 |
| ③ 불일치 ≥ 1건 | **배관 실패.** 유령 주문이면 **즉시 번인 중단**(실계좌였으면 규칙 밖 매매다). 누락이면 고치고 다시 5 거래일 |
| ④ 유지율 < 100% 또는 초과 매도 ≥ 1건 | **배관 실패.** 초과 매도는 실계좌에서 **돈이 새는 종류**라 우선순위 최상 |
| ⑤ 코드 결함 개입 ≥ 1건, 또는 무개입 < 4/5 | **고치고 다시 5 거래일.** 개입 분류표가 9단계 전 숙제 목록이다 |
| **다섯 개 전부 통과** | **배관 성립. 그래도 노선은 「보류」다**(§5). 9단계로 넘긴다 |

### 8.1 통과했을 때 9단계에 넘기는 것

성과가 아니라 **관측치와 사실**, 그리고 **안 잰 질문**이다.

1. **배관이 성립한다는 사실** — 네 종류가 나가고, 다리가 붙고, 정정되고, 상호
   취소된다.
2. **신뢰도 관문 전부** — 접수율·체결률 비율 문턱, 지각 0일, 무개입 완주 비율.
   **9단계 실계좌의 첫 관문이 이것이다**(7단계 §10-3). 성과 판정은 그 뒤다.
3. **15:50 스캔 ↔ 종가 확정 스캔 실측 불일치율**(§3.3) — 부호와 자릿수만.
   7단계 11.1% 는 IEX 프린트로 낸 하한이었다.
4. **MOC 체결가 vs 공식 종가 편차 관측치** — 페이퍼라 **하한**이라는 딱지를
   붙여서. 9단계에서 같은 자리를 실계좌로 재면 그게 7.7bp 질문의 절반이다.
5. **크론 넷의 기동 시각 분포와 멱등 발동 횟수** — 실계좌에서 같은 배선을 쓸지,
   자택 러너로 갈지의 입력이다.
6. **일일 정정 건수·실패 유형·rate limit** — 9단계 사이징 설계의 입력이다.
7. **개입 분류표**(§3.5) — 남은 자동화 숙제.

## 9. 이 측정이 **못** 하는 것 — 미리 밝힌다

- **슬리피지와 기대값을 못 잰다.** §4 전체. 7.7bp 는 이 문서로 안 좁혀진다.
- **신뢰도를 안 잰다 — 일부러다.** 비율 문턱이 없다(§1). 5일로 98% 를 말하면
  그건 신뢰구간이 아니라 희망이다. 9단계로 넘긴다.
- **마감 경매 체결을 못 본다.** 페이퍼는 경매에 참여하지 않는다. MOC 의 핵심
  질문이 그대로 남는다.
- **40봉 유지도, 자연 만기도 못 본다.** 5일째 강제 청산이다(§2.4). 밟는 건
  **코드 경로**이지 40봉 누적 표류가 아니다.
- **기업행위를 못 만난다.** 분할·병합·특별배당이 다리 가격을 어떻게 흔드는지
  5일 창에서는 안 나온다. **9단계 이전에 코드로만 방어하고, 관측은 못 한다.**
- **상장폐지를 못 만난다.** 판정 행 유니버스가 ADV 500만 · 5달러 위라 더 그렇다.
- **시장 국면이 하나다.** 5 거래일은 일주일이다 — 애초에 여기선 성과를 안 본다.
- **자본 제약이 배관에 섞인다.** 매수여력 부족으로 막힌 진입은 사전 등록된
  예외로 분류한다(§3.3). 자본·자리 제약 자체는 닫힌 노선이다
  (`pending-order-cash-block`).
- **실계좌만 보여주는 거절을 못 본다.** 대차 가능 여부, PDT, 마진, 계좌 상태,
  거래소 단위 규제 — 페이퍼는 전부 통과시킨다.
- **프로브는 체결 가격을 안 본다.** 경로만 본다(§3.1). 가격을 보면 §4 위반이다.
- **δ 를 다시 안 잰다.** 7단계의 δ(IEX, 2020-08 이후만, 15:50→15:59)를 갱신하지
  않는다. 이 문서는 δ 를 판정에 안 쓴다.
- **숏이 없다.** 판정 행이 롱만이라 원래 없던 것이지, 여기서 뺀 게 아니다.
- **러너도 계좌도 하나다.** 이중화·장애 복구를 안 본다.

## 10. 미리 밝히는 것 — 이미 본 숫자 전부

판정선을 적기 전에 본 것을 숨기면 사전 등록이 거짓말이 된다.
**7단계 측정 문서를 통째로 읽은 뒤에 이 문서를 썼다.**

**그래도 사전 등록이 성립하는 이유:** 이 문서의 판정선 다섯은 **전부 배관**이고,
아래 숫자 중 어느 것도 배관 문턱을 정하지 않았다. 성과 숫자를 다 본 상태에서
성과 문턱을 적었다면 그건 사전 등록이 아니지만, **여긴 성과 문턱이 없다**(§4).

**딱 한 군데, 이미 본 숫자가 설계를 바꿨다** — §0.1 의 「문턱을 δ만큼 내린 행」
(+2.5%, ① +0.031R)이 거짓 진입 걱정을 지웠고, 그래서 창을 20일에서 5일로
줄였다. **그건 판정 문턱이 아니라 달력 결정이다.** 그래도 여기 적어 둔다.

## 11. 도구 — 무엇을 새로 짜는가

### 11.1 `modules/alpaca_trading.py` — 주문 넷 추가

기존 함수 시그니처는 **한 줄도 안 바꾼다**(다른 러너가 쓴다).

| 새 함수 | 몸통 |
|---|---|
| `place_moc_buy(symbol, qty, ...)` | `side=buy` · `type=market` · `time_in_force=cls` |
| `place_moc_sell(symbol, qty, ...)` | `side=sell` · `type=market` · `time_in_force=cls` |
| `place_limit_sell(symbol, qty, limit_price, ..., tif="gtc")` | `place_limit_buy` 의 매도판 |
| `replace_order(order_id, ...)` | `PATCH /v2/orders/{id}` — 가격만 바꾼다 |

`place_stop_sell` 에 **`tif` 인자를 더한다**(기본은 지금 그대로 `"day"` —
기존 호출자가 안 바뀌게). 번인은 `tif="gtc"` 로 건다.

**두 다리 상호 취소는 러너가 한다**(브로커 OCO 를 안 쓴다). 매일 체결 확정
단계에서 포지션 수량이 0 이 되면 남은 다리를 취소. OCO 를 안 쓰는 이유는
`place_limit_buy` docstring 이 적은 그대로 — **bracket/OCO 는 백테스트가 잰 적
없는 체결 규칙**이라, 그걸 쓰려면 그 규칙을 따로 재야 한다. 여기서는 J-2·J-3 을
**있는 그대로** 두 개의 독립 주문으로 낸다.

### 11.2 `scripts/run_bitgak_paper.py` — 러너 하나, 모드 다섯

| 모드 | 언제 | 무엇 |
|---|---|---|
| `gate` | 사전 | §2.5 오프라인 선값 대조 |
| `probe` | 사전 | §3.1 스톱·지정가 체결 경로 |

`--dry-run` 은 `submit` 을 로그로만 돌린다(§6-5 의 드라이런 2일).
**규칙 계산은 `pilot_bitgak_power.scan()` 을 그대로 import 한다** — 러너가 규칙을

전부 · 선정 · 제출 · 접수 · 체결 · 정정 · 취소 · 예외 · 개입 · **크론 회차별
기동 시각**. **③ 대조는 이 파일 하나로 재현된다.**

### 11.3 `.github/workflows/bitgak-paper.yml`

- **크론 넷을 흩뿌린다**: 15:30 / 15:35 / 15:40 / 15:45 ET. 서머타임 때문에
  UTC 로는 EDT·EST 두 벌 = **여덟 줄**. 스크립트가 **ET 시계를 직접 검사**해서
  창 밖이면 즉시 종료 — 절반은 매번 헛돈다. `settle` 도 같은 방식.
- **멱등이 전제다.** 각 회차는 `bitgak8-{YYYYMMDD}-` 접두사로 오늘 주문을 먼저
  조회하고, 이미 있으면 아무것도 안 한다. `_find_by_client_order_id` 가 이미
  있다. **이게 없으면 크론 넷은 대책이 아니라 중복 주문 기계다**(§3.2).
- **휴장일은 크론이 모른다.** Alpaca 캘린더로 스크립트가 판정하고 조용히 종료
  (`index-autopilot.yml` 이 이미 쓰는 방식 — 날짜로 창을 넓게 잡고 안에서 판정).
- `runs-on: ubuntu-latest`. **지연은 ② 의 관측 대상이지 대책이 아니다** —
  대책은 크론 넷과 멱등이고, 그게 통했는지가 ② 다.

### 11.4 selftest — 새 8종

1. **MOC body 가 정확히** `type=market` · `time_in_force=cls` — 오타 하나면
   Alpaca 가 day 시장가로 받아 **장중에 체결**된다. 규칙이 아닌 매매가 된다.
2. **`place_stop_sell` 기본 호출이 지금과 글자 그대로 같은 body** — 기존 호출자
   회귀 방지.
3. **멱등** — 같은 날 `submit` 을 네 번 불러도 주문이 **한 번만** 나간다.
   §3.2 판정선의 단위 테스트판이고, 크론 넷의 전제다.
4. **`client_order_id` 접두사** — `bitgak8-` 없는 주문은 대조에서 제외되고,
   있는 주문은 전부 잡힌다. `bitgak8probe-` 는 장부·대조에서 빠진다.
5. **다리 상호 취소** — 합성 체결로 한쪽을 채우면 다른 쪽이 취소되고 **초과 매도
   0**.
6. **정정값 = 그날 하네스 선값** — §2.5 도구 게이트의 단위 테스트판.
7. **`--dry-run` 이 네트워크를 안 탄다** — 실수로 페이퍼에 주문이 새는 걸 막는다.
8. **장부 한 줄의 칸 수를 읽는 자리가 전부 세어졌는가** — 7단계 정오표 ⑤ 와
   PR #218 이 같은 병으로 물린 자리다. **행 모양을 바꾸면 그 행을 읽는 자리를
   전부 세어야 한다.**

## 12. 재현

```
# 0) 계좌 위생
python scripts/run_bitgak_paper.py clean            # 기존 포지션·주문 청소 (확인 프롬프트)

# 1) 달력을 안 쓰는 것부터
python scripts/measure_bitgak.py selftest           # 기존 산수 점검 (회귀)
python scripts/run_bitgak_paper.py selftest         # 신규 8종
python scripts/run_bitgak_paper.py gate --days 60   # §2.5 도구 게이트

# 2) 프로브 — 스톱·지정가 체결 경로 (§3.1)
python scripts/run_bitgak_paper.py probe

# 3) 드라이런 2 거래일 (판정 표본 아님)
python scripts/run_bitgak_paper.py scan
python scripts/run_bitgak_paper.py submit --dry-run

# 4) 번인 5 거래일 — 워크플로가 돌린다
#    .github/workflows/bitgak-paper.yml  (scan -> submit -> settle, 크론 넷)

# 5) 판정
python scripts/run_bitgak_paper.py report           # §1 다섯 판정선 + 부수 보고
```

실계좌는 이 저장소의 어떤 코드도 안 건드린다.
